## Gemini planning prompt (paste whole block)

```
You are a skeptical staff engineer reviewing a plan for an OPEN-SOURCE project.
Be concrete, prefer boring proven components, and flag licensing traps.

Project: Auris — ambient clinician–patient audio -> validated FHIR R4 resources
(Observation, Condition, MedicationRequest, AllergyIntolerance), with a SOAP
note rendered FROM the FHIR resources. Everything must run with open-weight /
OSS models self-hosted (no Claude/OpenAI APIs in the core path). Python.
Dev on Apple Silicon Mac; deployment target Linux (+ optional GPU).

Established facts from a fact-check of the original design note (do not
relitigate these):
- pyannote diarisation outputs anonymous speaker labels, NOT clinician/patient
  roles; role mapping is a separate component to design.
- JSON-Schema-valid != FHIR US Core profile-conformant (terminology bindings,
  FHIRPath invariants, slicing, mustSupport). A real validator stage is
  required and can fail; no "guarantee" language.
- Full FHIR R4 JSON schemas are recursive/reference-heavy; extraction must use
  hand-reduced schemas, then map to full resources.
- Evaluating an extractor on dialogues generated by the same model family, or
  on clean TTS audio, inflates scores. Real benchmarks (ACI-Bench 207
  dialogues, PriMock57) have note targets, not FHIR gold.

Proposed stack to critique:
1. ASR+alignment: faster-whisper or WhisperX (large-v3 / distil-large-v3)
2. Diarisation: pyannote.audio 3.x (gated models) vs NeMo Sortformer vs other
3. Role assignment: lexical/LLM classifier over diarised segments
4. Extraction: Qwen3-class local LLM via vLLM or Ollama, JSON-Schema
   constrained decoding (XGrammar/Outlines), reduced extraction schemas
5. Validation: HL7 FHIR Validator CLI with US Core IG + terminology checks;
   fhir.resources for Python-side structural checks
6. Note rendering: deterministic templates from validated resources only

Answer with:
(a) A per-stage recommendation with the strongest alternative and why;
(b) Licensing/redistribution traps (model weights, gated models, dataset terms)
    for an Apache-2.0/MIT repo;
(c) A 3-slice MVP roadmap where each slice is demoable end-to-end
    (suggest what to stub);
(d) An honest evaluation plan: gold FHIR annotation protocol, inter-annotator
    agreement, and how to use ACI-Bench/PriMock57 without faking FHIR gold;
(e) Top 5 failure modes in real clinic audio and a mitigation for each.
Keep it structured and specific: name exact libraries, model ids, and versions
where you can.
```
